cuBLAS

cuBLAS.jl offers NVIDIA's dense linear algebra library at three levels:

  • LinearAlgebra functions like *, mul!, dot, norm, axpy! and ldiv! with triangular matrices work on CuArrays, and should be the first choice.
  • The functions documented below wrap individual cuBLAS routines, for when more control is needed, or for operations that LinearAlgebra does not have, like batched products and factorizations. They are named after the BLAS routine they compute; the routines of cuBLASXt, which distribute large products over several GPUs and accept host memory, have an xt_ prefix.
  • The generated bindings in libcublas.jl and libcublasLt.jl follow NVIDIA's C API, and change with the CUDA toolkit. Use those in libcublas.jl together with handle; cuBLASLt needs its own handle, created with cublasLtCreate.

The wrappers follow LinearAlgebra.BLAS's conventions. Character arguments select the variant to compute (trans, uplo, side, diag), functions ending in ! overwrite their output argument, and the functions without ! allocate it. Unlike LinearAlgebra.BLAS, the level-1 functions take the number of elements first and read every array with its own stride, and some can write their result to a device-side scalar to avoid synchronizing. cuBLAS chooses between its 32-bit and 64-bit entry points automatically.

cuBLAS.enable_logging(enable::Bool=true)

Forward log messages from cuBLAS and cuBLASLt to Julia's logging system. API traces are reported at Debug level, performance hints at Info level, and problems at Warn or Error level. Starting Julia with JULIA_DEBUG=cuBLAS enables this automatically, and also shows the Debug-level messages.

cuBLAS.gemm! — Method
gemm!(transA, transB, alpha, A, B, beta, C; compute_type=nothing, algo=CUBLAS_GEMM_DEFAULT)

Compute C = alpha * op(A) * op(B) + beta * C, where op is selected by transA and transB ('N', 'T' or 'C'). The element types of A, B and C can differ, as long as cuBLAS supports the combination.

The compute type is selected based on these element types, e.g., computing products of Float16 matrices in Float16. Pass compute_type=Float32 to compute them in Float32 instead; Float16, Float64 and Int32 are supported as well. The math mode (see CUDA.math_mode!) then determines which variant of the compute type is used, e.g., computing Float32 products with TF32 tensor cores in fast math mode.

alpha and beta are numbers, or device-side scalars (e.g. a CuRef or a one-element CuArray) of the type cuBLAS expects for the selected compute type.

cuBLAS.gemm_batched! — Method
gemm_batched!(transA, transB, alpha, A, B, beta, C; compute_type=nothing,
              algo=CUBLAS_GEMM_DEFAULT)

Compute C[i] = alpha * op(A[i]) * op(B[i]) + beta * C[i] for every matrix in the vectors A, B and C. All products need to have the same size; see gemm_grouped_batched! for products of different sizes. Element types, scalars and the compute type are handled like for gemm!.

cuBLAS.gemm_grouped_batched — Function
gemm_grouped_batched(transA, transB[, alpha], A, B; kwargs...) -> C

Allocating version of gemm_grouped_batched!.

source
cuBLAS.gemm_grouped_batched! — Method
gemm_grouped_batched!(transA, transB, alpha, A, B, beta, C; compute_type=nothing)

Compute C[i][j] = alpha[i] * op(A[i][j]) * op(B[i][j]) + beta[i] * C[i][j] for every group i of matrices in the vectors of vectors A, B and C. The products in a group need to have the same size, but those in different groups don't. transA, transB, alpha and beta hold a value per group, or a single value for all of them.

With vectors of matrices for A, B and C, every product is a group of its own.

The element types of A, B and C need to be the same: Float16, BFloat16, Float32 or Float64. Products of 16-bit matrices are computed in Float32, and so are alpha and beta, which reside on the host. compute_type can only select that precision: Float32, or Float64 for Float64 matrices. Float16 and BFloat16 need cuBLAS 12.5, the other types cuBLAS 12.4.

cuBLAS.rotg! — Method
rotg!(a, b) -> a, b, c, s
rotg!(a, b, c, s) -> a, b, c, s

Construct the Givens rotation [c s; -conj(s) c] that zeroes out b, overwriting a with the rotated value (and, for real inputs, b with the reconstruction parameter).

When a and b are numbers, the results are returned as numbers. When they are device-side scalars (a CuRef or a one-element CuArray), they are updated in place and c and s are returned as device-side scalars as well, without synchronizing with the GPU. These outputs can be passed directly to rot!. Preallocated device-side c and s can be passed too.

cuBLAS.rotmg! — Method
rotmg!(d1, d2, x, y, param) -> d1, d2, x, y, param

Construct the modified Givens rotation that zeroes out the second component of (sqrt(d1)*x, sqrt(d2)*y), storing its flag and matrix in the 5-element param.

When d1, d2 and x are numbers, their updated values are returned as numbers. When they are device-side scalars (a CuRef or a one-element CuArray), they are updated in place without synchronizing with the GPU; y is only read and can be either.

Compute C = alpha * op(A) * B (side = 'L') or C = alpha * B * op(A) (side = 'R') for the triangular matrix A. Unlike LinearAlgebra.BLAS.trmm!, the result is written to C, which can be B itself. Wraps cublas<t>trmm.

cuBLAS.xt_gemm! — Function
xt_gemm!(transA, transB, alpha, A, B, beta, C) -> C

gemm! through cuBLASXt, which splits the product over the devices in xt_devices. The arrays can be in host or device memory, and the call returns when the result is ready. cuBLASXt does not follow stream ordering: device arrays must be ready when it is called, e.g. by synchronizing after the operations that compute them. Wraps cublasXt<t>gemm.
