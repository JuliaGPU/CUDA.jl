CUPTI

CUPTI, the CUDA Profiling Tools Interface, is what CUDA.jl's profilers are built on. Most users should use those instead: CUDA.@profile traces API calls and kernels, CUDA.@metrics collects hardware metrics for each kernel, and CUDA.@sample samples where kernels spend their time.

The module offers CUPTI at two levels:

  • The functions documented below wrap CUPTI's APIs for tools: callbacks on API calls and other events (CallbackConfig), tracing of activity such as kernel launches and memory copies (ActivityConfig), hardware metrics per kernel (range_profile) and PC sampling (pc_sample). They are not exported, so call them as CUPTI.range_profile(...).
  • The generated bindings in libcupti.jl follow NVIDIA's C API, and change with the CUDA toolkit. The records process passes and the enum values the configurations take come from there.

CUPTI reports two versions. CUPTI.version is the version of its API, which looks like a CUDA version and only changes when the API does, so check it for API features. CUPTI.library_version is the release of the library, which is numbered by year (e.g. v"2026.4.0") and changes with every CUDA update release, so it identifies a library with a known bug.

Profiling may need permissions: see can_profile, and NVIDIA's documentation on ERR_NVGPUCTRPERM for hardware metrics and PC sampling. A failing CUPTI call throws a CUPTIError.

CUPTI.CUPTI — Module

Julia wrappers for CUPTI, the CUDA Profiling Tools Interface, which CUDA.jl's profilers (CUDA.@profile, CUDA.@metrics, CUDA.@sample) are built on. See CUPTI.ActivityConfig, CUPTI.range_profile and CUPTI.pc_sample.

CUPTI.ActivityConfig — Type
CUPTI.ActivityConfig(activity_kinds::Vector{CUpti_ActivityKind}) -> ActivityConfig

Configuration for CUPTI's activity API, which records the given kinds of activity (e.g. CUPTI_ACTIVITY_KIND_CONCURRENT_KERNEL or CUPTI_ACTIVITY_KIND_MEMCPY) while the configuration is enabled with CUPTI.enable!, using cuptiActivityEnable. The records are kept in the configuration, and can be read afterwards with CUPTI.process. Activity kinds that the loaded CUPTI doesn't support are skipped.

cfg = CUPTI.ActivityConfig([CUPTI.CUPTI_ACTIVITY_KIND_CONCURRENT_KERNEL])CUPTI.enable!(cfg) do    # do stuffendCUPTI.process(cfg) do ctx, stream_id, record    # inspect recordend

CUPTI.CUPTIError — Type
CUPTIError

The exception the functions in this module throw when a CUPTI call fails. Its code field is the CUptiResult code, e.g. ERROR_INSUFFICIENT_PRIVILEGES when the user isn't allowed to profile, or ERROR_HARDWARE_BUSY when another process is using the profiling hardware.

source
CUPTI.CallbackConfig — Type
CUPTI.CallbackConfig(callback, domains::Vector{CUpti_CallbackDomain}) -> CallbackConfig

Configuration for CUPTI's callback API, which calls callback(domain, id, data) on every event in the callback domains (e.g. CUPTI_CB_DOMAIN_DRIVER_API or CUPTI_CB_DOMAIN_RESOURCE) while the configuration is enabled with CUPTI.enable!. id identifies the event (e.g. a CUpti_driver_api_trace_cbid for the driver API domain), and data is a copy of the record CUPTI passes, whose type depends on the domain: CUpti_CallbackData for the driver and runtime API domains, CUpti_ResourceData, CUpti_SynchronizeData or CUpti_NvtxData for the others. The copy is shallow: memory that the record points to, such as the arguments of an API call, is only valid until callback returns, so copy what you want to keep.

callback runs on the thread that triggered the event, possibly on several threads at once and while CUPTI or the driver hold internal locks. It must not yield, e.g. by doing I/O or waiting on a lock, and must not call the CUDA driver or runtime APIs, except for what CUPTI's documentation allows.

cfg = CUPTI.CallbackConfig([CUPTI.CUPTI_CB_DOMAIN_DRIVER_API]) do domain, id, data    # inspect dataendCUPTI.enable!(cfg) do    # do stuffend

CUPTI.PCSamples — Type
CUPTI.PCSamples

PC samples collected by CUPTI.pc_sample:

  • reasons: the name of every stall reason, by CUPTI's index;
  • pcs: for every sampled PC, keyed by the CRC of its cubin (as computed by CUPTI.cubin_crc), its function's name and the offset of the PC in that function, the number of samples per stall reason index;
  • total: the number of samples, including dropped ones and samples in kernels that CUPTI doesn't report (e.g. in the driver);
  • dropped: the number of samples that were lost because CUPTI's buffers were full.

CUPTI.ProfilerHost — Type
CUPTI.ProfilerHost(f, ctx::CuContext) -> result of f(host)

Create a profiler host object for the device of ctx, which configures and evaluates range profiler metrics, pass it to f, and return the result of f. The object is only valid while f runs, and its fields are not part of the API. Wraps cuptiProfilerHostInitialize, which needs CUPTI from CUDA 12.6 or later.

CUPTI.can_profile — Method
can_profile() -> Bool

Whether CUDA.jl should attempt to use CUPTI in the current process.

On Tegra, CUDA 10 through 12 require root, while CUDA 13 and later require read/write access to a profiling device node. This check is intentionally conservative because some CUPTI versions crash in cuptiSubscribe when that access is missing. On other systems, CUPTI reports permission errors normally, so this function returns true and lets CUPTI handle them.

CUPTI.enable! — Method
CUPTI.enable!(f, cfg::Union{CUPTI.ActivityConfig,CUPTI.CallbackConfig}) -> result of f()

Enable the activities or callbacks configured by cfg while calling f(), and return its result.

For an ActivityConfig, CUPTI's activity records are flushed into cfg when f returns (cuptiActivityFlushAll). Records of work that hasn't completed by then are incomplete or missing, so synchronize at the end of f. For a CallbackConfig, it subscribes to the configured callback domains (cuptiSubscribe and cuptiEnableDomain).

Only one configuration of each kind can be enabled at a time: an enable! in another task waits for the previous one to finish, while nesting enable! calls for the same kind of configuration in one task is not supported. CUPTI only supports a single callback subscriber per process, so a CallbackConfig can't be enabled while another tool (e.g. a profiler) is subscribed.

CUPTI.library_version — Method
CUPTI.library_version() -> VersionNumber

The release version of the loaded CUPTI library, e.g. v"2026.4.0", which recent CUPTI releases number by year. It changes with every release, so use it to work around bugs in a specific CUPTI library, and CUPTI.version to check for API features. CUPTI has no API for it, so it is read from the library's file name on Linux, as NVIDIA suggests, and from the DLL's version resource on Windows.

CUPTI.pc_sample — Method
CUPTI.pc_sample(f; ctx=context(), period=14) -> CUPTI.PCSamples

Sample the PCs of warps executing kernels in ctx while executing f(), once every 2^period cycles on each SM. Samples are only collected while f runs, so synchronize the context before calling pc_sample, and at the end of f, before it returns. Only one profiling session, of this function or CUPTI.range_profile, can be active at a time.

This uses CUPTI's PC sampling API (cuptiPCSamplingEnable and related routines) in continuous mode. This wrapper needs CUPTI from CUDA 13 or later (see CUPTI.has_pc_sampling) and a device that supports it (see CUPTI.check_pc_sampling_support).

Warning

With CUPTI 13.2 and later, loading a module after PC sampling was disabled makes enabling PC sampling or the range profiler fail with CUPTI_ERROR_INVALID_OPERATION, even in other contexts. Call cuptiFinalize when CUPTI isn't in use anymore (e.g., after unsubscribing from callbacks) to avoid that.

source
CUPTI.process — Method
CUPTI.process(f, cfg::CUPTI.ActivityConfig) -> nothing

Call f(ctx, stream_id, record) for every activity record collected in cfg, in the order CUPTI delivered them. ctx and stream_id are the CuContext (or nothing) and the CUPTI stream ID that CUPTI reported for the buffer holding the record. record is a copy of the record, as the newest CUPTI struct that the loaded CUDA version writes for its kind: e.g. CUpti_ActivityAPI for driver and runtime API calls, or CUpti_ActivityKernel9 for kernels on CUDA 12. Records of kinds this function doesn't know about are skipped with a warning. Wraps cuptiActivityGetNextRecord.

source
CUPTI.range_profile — Method
CUPTI.range_profile(f, metrics::Vector{String}; ctx=context(), max_ranges=1024)
    -> @NamedTuple{values::Matrix{Float64}, passes::Int}

Collect metrics for every kernel launched in ctx while executing f(), and return a named tuple with a ranges × metrics matrix of values and the number of passes each kernel was replayed. Ranges are numbered in the order the kernels executed, which is serialized by CUPTI; at most max_ranges kernels are profiled.

This uses CUPTI's range profiler in auto-range, kernel-replay mode, which needs CUPTI from CUDA 12.6 Update 2 or later (see CUPTI.has_range_profiler) and a device that supports it (see CUPTI.check_profiler_support). Only one profiling session, of this function or CUPTI.pc_sample, can be active at a time.

source
CUPTI.version — Method
CUPTI.version() -> VersionNumber

The version of CUPTI's API, e.g. v"12.9.1" or v"13.5.0", to check for API features. Wraps cuptiGetVersion. Before CUDA 13, CUPTI reports a revision number, which this function maps to the CUDA release that introduced it; several releases can share a revision (e.g. v"10.0" covers CUDA 10.0 to 10.2). From CUDA 13, CUPTI reports a version whose patch number is CUPTI's own. Either way, the version only changes when the API does, so it can't identify features or fixes added in an update release: look for the symbol of a new routine instead (as CUPTI.has_range_profiler does), or use CUPTI.library_version.
